# Версионирование конфига

`master` содержит проверенный рабочий конфиг. Для крупных изменений создавай
короткие ветки, после проверки объединяй их с `master`.

Коммиты описывают отдельные изменения (`feat:`, `fix:`, `chore:`).
Теги отмечают проверенные состояния; каждому коммиту версия не нужна.

## Номера версий

Используем аннотированные теги `vMAJOR.MINOR.PATCH`:

- `patch`: исправления без намеренного изменения привычного поведения;
- `minor`: новые возможности, плагины или изменения сочетаний клавиш;
- `major`: масштабная несовместимая перестройка конфига.

Первый релиз — `v0.1.0`. До `v1.0.0` несовместимые изменения допустимо
выпускать как minor, но их нужно описывать в сообщениях коммитов.

## Подготовка

1. Проверь запуск Neovim, `:checkhealth` и затронутые сценарии работы.
2. Коммить `init.lua` и `nvim-pack-lock.json`. Обновления плагинов по возможности
   делай отдельными коммитами.
3. В README указывай проверенную версию Neovim и необходимые внешние инструменты.
   Lock-файл фиксирует плагины, но не Neovim, LSP, форматтеры или все артефакты
   установки. Один Git-тег не гарантирует полное восстановление окружения.
4. Переключись на `master`, объедини проверенные изменения и закоммить всё нужное.
   Логи и другие служебные файлы не должны попадать в Git.

## Утилита релиза

Запускай из любой директории, указав путь к скрипту:

```sh
./scripts/release --dry-run       # посмотреть следующую версию
./scripts/release                 # patch; первый релиз — v0.1.0
./scripts/release minor           # например v0.1.2 → v0.2.0
./scripts/release major
./scripts/release v0.3.0          # явный номер
./scripts/release minor --push    # создать тег и отправить master + тег
```

Нужны Bash и Git. Скрипт требует чистое рабочее дерево и ветку `master`,
выбирает максимальный стабильный тег `vX.Y.Z`, проверяет увеличение версии
и наличие новых коммитов. Он не коммитит файлы и не запускает Neovim.
Без существующих тегов любой автоматический bump создаёт `v0.1.0`;
для другого первого номера укажи его явно.

По умолчанию тег создаётся только локально. `--push` сначала получает `master`
и теги из `origin`, затем отправляет ветку и тег одной атомарной операцией.
Перед локальным релизом на нескольких машинах сначала выполни
`git fetch origin --tags`, чтобы иметь актуальный список версий.
`--dry-run --push` также выполняет fetch, но не создаёт и не отправляет тег.

Если push завершился ошибкой, локальный тег сохраняется. После устранения
причины отправь уже созданный релиз:

```sh
git push --atomic origin master v0.3.0
```

Утилита создаёт Git-тег; отдельную страницу GitHub Release она не создаёт.

## Просмотр прошлой версии

```sh
git log --oneline v0.1.0..v0.2.0
git show v0.1.0:init.lua
```

Для возврата настроек создай новый коммит с нужными изменениями. Если
возвращаешь lock-файл, также приведи установленные плагины к указанным в нём
ревизиям. Опубликованные теги не перемещай: исправление выпускай новой версией.
